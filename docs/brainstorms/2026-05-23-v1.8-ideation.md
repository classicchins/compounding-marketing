# v1.8 Ideation — Multi-Surface Delivery + Compounding Architecture

## TL;DR

The plugin ecosystem has formalized around two specs in the last 8 months: **Agent Skills** (Anthropic, December 2025 — now 32+ adopters including Codex, Cursor, JetBrains, Goose, Gemini CLI) and **AGENTS.md** (Linux Foundation Agentic AI Foundation, December 2025 — adopted by ~15 tools). Our v1.6 architecture is structurally aligned with both, but we are missing three concrete wins the field has converged on:

1. **Skills-as-commands unification.** Both Superpowers and compounding-engineering have collapsed `commands/` into `skills/`. We still maintain two parallel directories. Collapsing them removes a category of cognitive overhead and aligns with the Agent Skills spec.
2. **Sub-agent tier for parallel work.** Compounding-engineering dispatches 6–9 parallel specialist agents from a single skill (e.g., `ce-code-review` runs 6 reviewers in parallel). We do everything serially in-skill. For research-heavy or multi-perspective skills (`/cm-research`, `/cm-audit`, `/cm-position`), a sub-agent tier is dramatically more powerful.
3. **Learnings consumption beyond manual lookup.** Our v1.7 work wires Prior Learnings Consulted in 5 skills (read side) and rebuilds `/cm-compound` (write side). The next leverage is a dedicated `cm-learnings-researcher` agent with a frontmatter-first search pattern (compounding-engineering uses this), so we don't re-scan the whole vault on every skill run.

On surfaces: we are **already covered** for Codex Desktop App (it shares all config with Codex CLI). The genuinely new lever is **Cursor plugin format** (`.cursor-plugin/` with `marketplace.json`) — medium effort, unlocks the Cursor Marketplace + team admin distribution that shipped May 2026. **Claude Desktop App is structurally low-leverage** for our use case (no skill surface — only MCP prompts).

Recommended v1.8 scope (8–12 PRs across ~3 weeks): skills/commands collapse, sub-agent tier on 3 high-leverage skills, learnings-researcher agent, Cursor plugin packaging, Claude Code `.claude/skills/` migration with `when_to_use` frontmatter, AGENTS.md spec alignment audit.

| Hooks | None | Intentional gap |

What's strong: the 7-section template + validator gives consistency guarantees the reference projects trade away. Our `npx` wizard with merge prompts is safer than Superpowers' silent overwrite or compounding-engineering's delegation to native plugin systems. Skills are written for marketing depth (each ~300–700 lines), not stubs.

What's weak: skills and commands are two parallel paradigms with overlapping mental models. Every skill that does research, audits, or multi-perspective review runs all of it serially in one prompt. There is no programmatic learnings retrieval — `.agents/learnings/` files are read by the model directly, which scales poorly past a few entries per category. The plugin ships as a setup-wizard artifact, not as a packaged plugin in any platform's marketplace.

## 2. Where the field is going (signals from 2025-Q4 → 2026-Q2)

### Agent Skills spec — now the lowest common denominator for skills
- Published by Anthropic December 18, 2025.
- 32+ adopters by March 2026: VS Code, OpenAI Codex (within 48h of release), Cursor, JetBrains Junie, Sourcegraph Amp, Block Goose, Snowflake, Databricks, Google Gemini CLI, ByteDance, Mistral, Factory Droids.
- A SKILL.md written to the spec is structurally portable. Discovery paths differ per tool but the file format is identical.
- New 2026 frontmatter keys we don't use: `when_to_use`, `paths` (glob auto-load), `hooks` (skill-scoped), `disable-model-invocation`, `argument-hint`, `${CLAUDE_SKILL_DIR}` substitution, `model`, `effort`, `agent`.

### AGENTS.md formalized + adopted broadly
- Donated to Linux Foundation Agentic AI Foundation (AAIF), December 2025.
- 146 member orgs by February 2026.
- Read by: Claude Code, Codex CLI, Cursor, Aider, Devin, Sourcegraph Amp, Google Jules, Zed, Continue, Roo Code, Factory Droids, GitHub Copilot, Gemini CLI, Windsurf, Amazon Q.
- Our wrapped-block merge pattern is now the industry standard. No change needed; we are already correctly aligned.

### Claude Code: `.claude/skills/` is canonical going forward
- As of May 2026, `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both register `/deploy`. Skills take precedence on collision.
- New work should target `.claude/skills/` ; `.claude/commands/` stays for backward compatibility.
- We install to `.claude/commands/`. That still works but we should migrate.

### Codex CLI + Codex Desktop App share config
- All of `~/.codex/config.toml`, `~/.codex/skills/`, `~/.codex/AGENTS.md`, MCP servers — shared between CLI and Desktop App.
- **Implication: there is no separate "Codex Desktop App" install target.** Our existing Codex CLI install path covers both.

### Claude Desktop App is MCP-only for plugin purposes
- Config: `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS).
- Supports: MCP servers, custom instructions (one global system prompt), Desktop Extensions (1-click MCP install).
- Does **not** support: custom slash commands, skills, CLAUDE.md/AGENTS.md, file-system-aware projects.
- To deliver compounding-marketing skills to Claude Desktop, we would need to **build an MCP server** that exposes skills as MCP `prompts`. Non-trivial engineering; defer unless there is demand.

### Cursor plugin marketplace + team controls (May 2026)
- `.cursor-plugin/` directory with `marketplace.json`, `skills/`, `rules/`, MCP definitions is now a packaged distribution surface.
- Team marketplace controls shipped May 1, 2026: Default Off / Default On / Required distribution.
- Audience: orgs that standardize tooling for their marketing teams.

### Cross-cutting trend: MCP for tools, Skills for procedures
- MCP carries tool calls and resource access — same across all 6 surfaces.
- Agent Skills carries procedural knowledge — same file format everywhere with different discovery paths.
- They are complementary layers, not substitutes. We use both today; nothing to change architecturally.

## 4. v1.8 candidate features — ranked by leverage

### Tier S — should-ship-in-v1.8

**S1. Collapse `commands/` into `skills/`.**
Source: compounding-engineering, Superpowers. Cursor and Claude Code's 2026 spec confirms: skills *are* commands. Maintaining both is historical drag. Plan: each `commands/cm-*.md` becomes a SKILL.md in `skills/cm-*-workflow/` (or a workflow folder), with `argument-hint` frontmatter. Setup wizard installs the lot to `.claude/skills/` (with a backward-compat write to `.claude/commands/` until v2.0). Validator extends to cover workflows. Net: one mental model, fewer files, aligned to Agent Skills spec.
Effort: medium. Risk: medium (touches every workflow + wizard install paths).

**S2. Sub-agent tier — pilot in 3 skills.**
Source: compounding-engineering. Pilot in `/cm-research`, `/cm-audit`, `/cm-position` — each benefits from parallel specialist perspectives. Pattern: skill orchestrates, dispatches 3–5 specialist agents (e.g., `cm-icp-finder`, `cm-competitor-mapper`, `cm-positioning-canvas-runner`), merges results. Implementation needs cross-platform dispatch helper (Claude Code uses Agent tool; Codex uses `spawn_agent`; Cursor uses `Subagent`). Write a `references/sub-agent-dispatch.md` doc that skills consult.
Effort: high. Risk: medium (cross-platform dispatch is the hard part; behavior diverges by platform).

**S3. `cm-learnings-researcher` agent + frontmatter-first search.**
Source: compounding-engineering. Right now wired skills read `.agents/learnings/<category>.md` directly. That's fine at 5 entries; it breaks at 50. Build a dedicated researcher agent that: (1) reads only frontmatter from the category file, (2) scores entries by relevance to current request, (3) full-reads only top 3. Skills call the researcher; the section's behavior stays identical from the user's POV. Pairs with adding richer frontmatter to learnings entries (`tags`, `linked_projects`, `last_referenced`).
Effort: medium. Risk: low (additive, can fall back to direct read if researcher not available).

**S4. Cursor plugin packaging.**
Source: multi-surface research. Build `.cursor-plugin/` directory with `marketplace.json`, `skills/` (link or copy), `rules/` (one `.mdc` per workflow), MCP entries. Publish to Cursor Marketplace. Unlocks team admin controls. Skill files themselves don't change — just packaging.
Effort: low–medium. Risk: low. Pure additive distribution win.

**S5. Claude Code `.claude/skills/` migration with `when_to_use`.**
Source: multi-surface research. Update setup wizard to install primarily to `.claude/skills/`. Keep `.claude/commands/` write for backward compat. Add `when_to_use` frontmatter to all 61 skills for better auto-triggering. Migrate frontmatter to include the new Agent Skills 2026 fields where applicable.
Effort: low (mostly wizard + bulk frontmatter edit). Risk: low.

### Tier A — strong candidates

**A1. Headless mode (`mode:headless`).**
Source: compounding-engineering. Add a `mode` argument to `cm-compound`, `cm-audit`, `cm-retro`, `cm-weekly` so they can run without interactive prompts and produce machine-readable output. Enables CI integration and scheduled use (e.g., weekly retro auto-generated from CRM data).
Effort: medium. Risk: low.

**A2. Skills-as-commands `cm-skill-author` meta-skill.**
Source: Superpowers' `writing-skills` skill. A skill that generates structurally valid SKILL.md files following our 7-section template. Reduces the friction of contributing a new skill (currently described in CLAUDE.md but manual). Runs `validate-skills.js` as a post-step. Could optionally accept a marketing tactic or framework name and stub out the template.
Effort: low. Risk: low. Compounds the framework itself.

**A3. `STRATEGY.md` layer above `product-marketing-context.md`.**
Source: compounding-engineering. Short top-of-stack file (1 page) with target problem, ICP, key metrics, **active tracks of work** (e.g., "Q3 launch", "Q3 SEO push", "Q3 pricing test"). Every planning skill reads it and flags when a request diverges from active tracks. `product-marketing-context.md` stays as the longer reference; `STRATEGY.md` is the focus layer. New skill `/cm-strategy` writes and maintains it.
Effort: medium. Risk: low.

**A4. Per-project config (`.compounding-marketing/config.local.yaml`).**
Source: compounding-engineering. Gitignored per-project file for behavioral preferences (output verbosity, default brand voice intensity, research depth, headless default). Setup wizard writes the example; the local file is created on first interactive use. Skills check it for runtime defaults.
Effort: low. Risk: low.

**A5. Learnings file schema v1.1 — richer frontmatter for retrieval.**
Source: claudesidian (Nexus). Add optional `tags`, `linked_projects`, `last_referenced`, `success_signals` fields to each entry. Backward compatible (v1.0 entries continue to work). Researcher agent (S3) uses these for relevance scoring without full-reading entries.
Effort: low. Risk: low.

### Tier B — defer or watch

**B1. Hook system.**
Source: Superpowers. Superpowers' PreToolUse bash-compression hook, SessionStart bootstrap hook, and PostToolUse edit-tracking are useful, but Claude Code-only — they break on Cursor and Codex. compounding-engineering explicitly avoids hooks for this reason. **Recommendation: don't ship hooks in v1.8.** Maybe a small SessionStart bootstrap that loads `product-marketing-context.md` automatically, gated behind an opt-in flag.

**B2. Claude Desktop App MCP server.**
Source: multi-surface research. Requires building an MCP server that exposes skills as MCP prompts. Significant engineering. Audience overlap with Claude Code is very high (most Claude Desktop power users also use Claude Code). Defer until there's specific demand.

**B3. Workspace-scoped learnings.**
Source: Nexus. Per-project namespaces (`.agents/projects/<slug>/learnings.md`) plus cross-project synthesis. Useful for agencies/orgs running compounding-marketing across many client accounts. We don't yet have user signal that this matters for solo founders / single-product teams. Defer to v1.9.

**B4. Symlink-based multi-surface delivery.**
Source: claudesidian (Noah). Install once to a canonical location, symlink into per-tool skill dirs. Cleaner than current copy-write approach but cross-platform symlink behavior is messy (Windows). Net not clearly better than what the wizard does today. Defer.

**B5. Local semantic search over learnings (sqlite-vec).**
Source: Nexus. Beautiful pattern but heavy lift — requires a binary dependency and indexing. Frontmatter-first search (S3) covers ~80% of the value at <5% the complexity. Defer.

**B6. `lfg`-style full-autonomy pipeline.**
Source: compounding-engineering. A `/cm-lfg` that runs the full /cm-research → /cm-position → /cm-copy → /cm-launch loop unattended. Interesting but premature — risk of producing low-quality output without human checkpoints. Marketing is higher-stakes than code review on this dimension. Defer.

## 6. Open questions for decision

1. **Skills-as-commands collapse (S1) — flat vs. tagged?** Two options for representing the 16 workflow commands inside `skills/`:
   (a) Flat: each workflow becomes `skills/cm-research/SKILL.md` next to `skills/icp-research/SKILL.md` (61 + 16 = 77 skills).
   (b) Tagged: add a `kind: workflow | skill` field; treat workflows differently in catalog UI and validator.
   (a) is simpler and matches what compounding-engineering does. (b) preserves the distinction the user docs already make. Recommend (a) — but call this out for confirmation.

2. **Sub-agent pilot — which 3?** Above I picked `/cm-research`, `/cm-audit`, `/cm-position`. Alternatives: `/cm-launch` (parallel: PR plan, channel plan, copy plan, analytics plan), `/cm-copy` (parallel: H1 variants, body, CTA, social proof), `/cm-email` (parallel: subject, sequence, deliverability). Worth user input — which workflows feel most "stuck" today and most likely to benefit?

3. **Cursor plugin — publish to Marketplace, or just structure-the-files?** Publishing to the Marketplace requires review and ongoing maintenance. Structuring the files but not publishing keeps the option open without commitment. Recommend: structure now, publish in v1.8.1 once stable.

4. **Claude Desktop App — defer or partial?** A minimal MCP server that exposes only `/cm-context` and `/cm-research` (the two most universally useful) might be lower-effort than I've assumed. Worth a 1-day spike to size it. If small, fold into S4.

5. **Hook policy.** Hard no on hooks for v1.8, or open the door to one specifically (e.g., SessionStart context loader)? My recommendation is hard no — preserves cross-platform parity, matches compounding-engineering's principled stance. But Superpowers' bash-compress hook is genuinely clever and might be worth a Claude Code-specific opt-in extension.

6. **Naming.** Two minor cleanups: (a) repo currently has the v1.7-ideation branch with a schema file — should we name the schema work itself "v1.7" (and ship it as a small release) or fold it into v1.8? (b) The 16 workflow commands prefixed `cm-*` could conflict with collapsed skills. Recommend a `cm-flow-*` prefix for collapsed workflows to disambiguate (e.g., `/cm-flow-launch`). Up to the user.

## 7. Late-add: Integration auto-detection (raised 2026-05-23)

> **Question raised by user:** "Claude Code and Codex App installs will already have tools/apps/integrations connected in the client (Slack, Notion, Linear, etc.). Will our installer identify all those and update any required workflows based on the availability on the device? Or do you suggest this for v1.9?"

**Recommendation: two-phase split. Ship lightweight *detect + surface* in v1.8. Defer deep *workflow adaptation* to v1.9.**

The detection part is small. The workflow adaptation part is large. Bundling them collapses the v1.8 timeline; splitting them lets us ship the user-visible win quickly and earn the design feedback we need before doing the per-skill work.

### What's actually feasible

By 2026-Q2 the per-tool MCP config locations are well-defined and machine-readable. A scan-and-surface pass can run during `npx compounding-marketing` install (or as a standalone `/cm-context` subcommand) without any new abstractions.

| Surface | Where integrations live | Format | Detectability |
|---|---|---|---|
| Claude Code (project) | `.mcp.json` at repo root | JSON `{"mcpServers": {...}}` | trivial |
| Claude Code (global) | `~/.claude.json` (state) + `claude mcp list` | JSON, also CLI | trivial via CLI |
| Claude Desktop App | `~/Library/Application Support/Claude/claude_desktop_config.json` (macOS) / `%APPDATA%\Claude\` (Windows) | JSON `{"mcpServers": {...}}` | trivial |
| Codex CLI / Codex Desktop App | `~/.codex/config.toml` (shared) | TOML `[mcp_servers.<name>]` | trivial |
| Cursor | `.cursor/mcp.json` (project) + `~/.cursor/mcp.json` (global) | JSON | trivial |
| Zed | `~/.config/zed/settings.json` under `context_servers` | JSON | trivial |

Server-name → integration mapping is also straightforward in the common case (`@modelcontextprotocol/server-slack` → Slack; `@notionhq/notion-mcp-server` → Notion; `@linear/mcp-server` → Linear; `@hubspot/mcp-server` → HubSpot, etc.). For unknown packages we fall back to surfacing the raw server name.

### Phase 1 — Detect + surface (v1.8, ~1 week)

Scope is intentionally narrow:

- **New install step:** "**Integrations** — scanning your installed AI tools for available connections…" The wizard reads the per-tool MCP config files for the chosen `--tool` (and `--scope=global` paths if applicable), parses them, maps known server packages to friendly names, and prints a summary:

  ```
  Detected integrations:
    ✓ Slack    (claude-desktop, codex)
    ✓ Notion   (claude-desktop, claude-code-global)
    ✓ Linear   (codex)
    ? unknown  (cursor)  — server: @acme/internal-mcp
  ```

- **Writes a context manifest:** `.agents/integrations.md` — a short, machine-readable markdown file listing detected integrations, the surfaces they were detected on, and the canonical capability tags (`slack:messaging`, `notion:docs`, `linear:tickets`, `hubspot:crm`, `stripe:billing`). Updated on every `/cm-setup` re-run.

- **Surfaces in `product-marketing-context.md`:** The detected integration list is referenced in the context file's "Available tools" section (or a new section if missing). Wired skills can read it as ambient context — no per-skill code changes required.

- **One opt-in summary in the install summary:** "3 integrations available — skills with marketing-relevant connections (Notion docs for content-strategy, Slack for community-strategy, HubSpot for icp-research) will surface them in their suggestions." Non-actionable today; purely informational.

**What v1.8 explicitly does NOT change:**

- Skill prompts themselves. No `if Slack available, do X` branches inside SKILL.md.
- Workflow command bodies. `/cm-launch` still runs the same steps regardless of whether Slack MCP is connected.
- No fallback logic. The integrations file is a passive context document, not a router.

**Why this is the right v1.8 cut:**

1. **Low blast radius.** It's an additive read + a single new file write. The current install flow is unchanged for users who decline to scan.
2. **Earns design feedback.** Once users see the `.agents/integrations.md` file, we'll learn which integrations they actually have, which mappings are wrong, and which capability tags matter — *before* we encode them into 61 skills.
3. **Compounds with the v1.7 schema philosophy.** The integrations file mirrors the learnings file shape: machine-readable, ambient context, surfaced to skills via convention.

**Risks:**

- Permission to read MCP config files outside the project root. The wizard already touches `~/.claude`, `~/.codex`, `~/.cursor`; reading them with explicit prompt is consistent with current behavior.
- Privacy: an MCP config can reveal what tools a user runs (e.g., a private analytics MCP). Mitigate by storing only the integration *names* and capability tags in `.agents/integrations.md`, never the server URLs or credentials. Make the scan opt-in with a clear prompt.
- Stale data: integrations change. v1.8 surfaces the date the scan ran; users can re-run by invoking `/cm-setup` or a new `/cm-detect-integrations`.

### Phase 2 — Workflow adaptation (v1.9, ~3 weeks on its own)

This is where the real leverage lives, and why it deserves a dedicated release.

- **Per-skill integration hooks.** Each wired skill grows a section after Prior Learnings Consulted called **Integrations Available**, which reads `.agents/integrations.md` and conditionally adjusts the deliverable:
  - `content-strategy` → if Notion: produce the editorial calendar directly in Notion via MCP; if not: produce markdown.
  - `icp-research` → if HubSpot or Salesforce: pull real cohort firmographics; if not: prompt user for CSV.
  - `community-strategy` → if Slack: include a Slack channel architecture; if not: platform-agnostic.
  - `case-study` → if Notion or Linear: pull customer references from those systems before drafting.
  - `email-sequence` → if HubSpot/ActiveCampaign/Marketo/Klaviyo: produce the workflow in that platform's terms.

- **Capability-tag taxonomy.** A canonical set of tags (`crm`, `docs`, `messaging`, `tickets`, `analytics`, `billing`, `email`, `cdp`) so skills branch on capability, not vendor name. Skills work whether the user has HubSpot or Salesforce; both expose `crm`.

- **Fallback contract.** Every integration-aware skill ships a "without this integration" path. We never block on absence.

- **New skill: `/cm-integrations`.** Manages the integrations file directly, runs a diff against a fresh scan, lets the user toggle capability tags on/off.

**Why this is v1.9, not v1.8:**

- It touches 30+ skills (every skill where a marketing tool meaningfully changes the output). That's a 7-section template edit pass plus per-skill testing.
- It needs the capability-tag taxonomy designed, validated, and stable — which requires real-world feedback from Phase 1 users.
- It changes skill behavior visibly. Doing it before we know what users actually have plugged in risks designing for the wrong integrations.
- v1.8 is already 8 work items; adding 30+ skill edits pushes past 6 weeks.

### Decision

Add to **Stream 1 (Architecture)** of v1.8 scope:

- **S6 (new). Integration auto-detection — Phase 1.** Read per-tool MCP configs during install, write `.agents/integrations.md`, surface in install summary, reference in `product-marketing-context.md`. ~1 week, low risk.

And add to the v1.8 doc's "Out of v1.8 (explicitly)" list:

- Per-skill integration-aware behavior — designed in v1.9 after Phase 1 ships and we see what users actually have connected.

**Open questions for the user on this addition:**

2. Should `.agents/integrations.md` live under `.agents/` (visible) or `.compounding-marketing/` (gitignored)? Recommend `.agents/` so it's visible alongside `product-marketing-context.md` — but redact server URLs.
