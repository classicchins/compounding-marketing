## P1 — High

### #1 — Broken relative link in `_TEMPLATE.md`
**File:** `skills/_TEMPLATE.md:45`
**Reviewer:** project-standards (confidence 100) · **Route:** safe_auto → review-fixer

The link `[skills/_LEARNINGS_SCHEMA.md](../_LEARNINGS_SCHEMA.md)` resolves to repo root from `skills/_TEMPLATE.md`. Correct target is `(_LEARNINGS_SCHEMA.md)`.

The 5 wired skills at `skills/<skill>/SKILL.md` are one level deeper and use the same `(../_LEARNINGS_SCHEMA.md)` pattern correctly. Only the template itself is broken. Authors copy/pasting from `_TEMPLATE.md` will inherit a working link in their nested skill, but the template's own link is dangling.

### #2 — "Six required fields" miscount in `cm-compound.md` Step 3
**File:** `commands/cm-compound.md:48-61`
**Reviewers:** correctness · maintainability · agent-native · api-contract (cross-reviewer promote — confidence 100) · **Route:** safe_auto → review-fixer

Step 3 is headed "Draft the six required fields" but enumerates 7 numbered items (Title + Context + Finding + Evidence + Implication + Linked skills + Confidence). Step 4 validates only 6 (Title is a heading, not a bullet). Schema doc says 6 bulleted fields.

An LLM following Step 3 may emit `- **Title:** …` as a bullet and corrupt the schema. This is the highest agent-native risk in v1.7.

**Suggested fix:** rewrite Step 3 to "First, establish the entry title (one line, ≤120 chars, becomes the H2 heading after the date). Then collect the six required fields in this order:" and renumber bullets 1–6 to match Step 4.

### #3 — Phantom `schema:` frontmatter field
**Files:** `skills/_TEMPLATE.md:61`, `commands/cm-compound.md:81-85`, `skills/_LEARNINGS_SCHEMA.md:39-46`
**Reviewers:** correctness · api-contract (cross-reviewer promote — confidence 100) · **Route:** safe_auto → review-fixer

`_TEMPLATE.md` Step 2 tells readers to "Confirm `schema` is `learnings`." `cm-compound`'s file-creation template writes only `category`, `last_updated`, `entries_count`. Schema doc's "Required YAML frontmatter" block also lists only those three. Every learnings file produced will always hit the "implicit/legacy" branch — the explicit confirmation branch is unreachable.

Three sources disagree on whether a 4th frontmatter key exists.

**Suggested fix:** remove the "Confirm `schema` is `learnings`" instruction from `_TEMPLATE.md` Step 2. (Less write-side overhead than adding it to cm-compound's template.)

### #4 — False "positional parsing" claim
**Files:** `skills/_LEARNINGS_SCHEMA.md:55`, `skills/_TEMPLATE.md:45`
**Reviewers:** correctness · maintainability · api-contract (cross-reviewer promote — confidence 100) · **Route:** safe_auto → review-fixer

Schema and template both say "wired skills parse positionally as well as by label, so do not reorder." No reader actually parses by position — all 5 wired skills + the template select entries semantically by label match. The constraint is documented as a hard technical requirement that doesn't exist, and will incorrectly force major-version treatment on any future field reordering in v1.1+.

**Suggested fix:** replace with "wired skills parse by label, but bullet field names and order must match the schema exactly so future parsers can rely on either dimension."

## P2 — Moderate

### #5 — Triplication of contract steps across 5 wired skills
**Files:** all 5 wired SKILL.md files
**Reviewer:** maintainability (confidence 90) · **Route:** gated_auto → downstream-resolver

Steps 1/2/4/5 of the 5-step consumption contract are near-verbatim across the 5 wired skills + `_TEMPLATE.md` + `_LEARNINGS_SCHEMA.md` (7 locations). Only Step 3's match-criteria bullets and the "Common high-leverage learnings" coda are genuinely per-skill.

v1.8 rollout to 56 more skills compounds the maintenance debt.

**Fix:** collapse non-skill-specific steps to a single reference to `_LEARNINGS_SCHEMA.md`; keep only Step 3 bullets + coda per skill. ~15 lines saved per skill (~75 total).

### #6 — `PRIOR_LEARNINGS_WIRED` hardcoded Set in validator
**File:** `scripts/validate-skills.js:31-37`
**Reviewer:** maintainability (confidence 85) · **Route:** gated_auto → downstream-resolver

Hardcoded list with no structural coupling to which files actually contain the heading. A `PRIOR_LEARNINGS_HEADING` regex already exists; a self-describing approach (any skill matching the regex is "wired by definition") would remove the manual sync burden during the 56-skill rollout. **Cut over before the list passes ~10 entries.**

### #7 — Stale "7-section structure" in authoring docs
**Files:** `CLAUDE.md:107`, `AGENTS.md:20,98`
**Reviewer:** project-standards (confidence 75) · **Route:** safe_auto → review-fixer

CLAUDE.md §"Adding a New Skill" step 2 still says "the validated 7-section structure" and lists 7 sections. AGENTS.md §"How skills work" and §"Quality Standards" say "7-section body" and "all 7 sections present." The 5 wired skills now ship 8 sections.

New v1.7 sections were added describing the system, but the authoritative authoring checklist was not patched.

**Fix:** add a sentence: "Plus an optional Prior Learnings Consulted section before Process — copy from `_TEMPLATE.md` if your skill should compound knowledge."

### #8 — CHANGELOG misstates validator skip mechanism
**File:** `CHANGELOG.md` (v1.7.0 §Added)
**Reviewer:** project-standards (confidence 75) · **Route:** safe_auto → review-fixer

Says `_LEARNINGS_SCHEMA.md` is skipped "via the existing `_*` prefix rule." Actual code skips files named `_TEMPLATE.md` or files inside `_*`-prefixed *directories*. `_LEARNINGS_SCHEMA.md` is skipped only because the discovery loop builds `skills/<dir>/SKILL.md` paths and flat files are never enumerated.

### #9 — Forward-compatibility unoperationalized
**Files:** `skills/_LEARNINGS_SCHEMA.md:172`, 5 wired skills, `_TEMPLATE.md`
**Reviewers:** api-contract · learnings (cross-reviewer promote — confidence 100) · **Route:** safe_auto → review-fixer

Schema says "forward-compatible" but no consumer instruction says what to do with unknown bullet fields. The v1.8 brainstorm A5 proposes adding `tags`, `linked_projects`, `last_referenced`, `success_signals`. A v1.0 reader has no documented behavior on a 7th bullet.

**Fix:** one sentence in `_TEMPLATE.md` Step 3 + each wired skill: "Bullet fields beyond the six required are safe to ignore — the schema is forward-compatible."

### #10 — First-entry insertion ambiguity
**Files:** `commands/cm-compound.md:77-98`, `skills/_LEARNINGS_SCHEMA.md:161-163`

Step 6 says "above the most-recent existing entry." When `entries_count: 0`, no entry exists. The intro template ends with `---`; the model has no explicit instruction whether the first entry goes before or after that rule.

### #11 — "Wired in v1.7 for: …" blockquote in `_TEMPLATE.md`

## Residual Risks

- **No round-trip verification** between cm-compound write and wired-skill read. No fixture file, no parse script confirms write→read symmetry.
- **`entries_count` drift** is enforced only at write-time by the LLM following cm-compound; no offline check.
- **Validator no longer exits 1 unconditionally** — only when `failures.length > 0`. CI that relied on non-zero-on-any-issue passes silently on schema regressions.
- **AGENTS.md and CLAUDE.md both carry compressed 5-step contract summaries** that already diverge in wording.
- **Same-date collision suffix** — cm-compound specifies "— part 2"; schema says only "disambiguating suffix." Drift risk.
- **`PRIOR_LEARNINGS_WIRED` rollout debt** — as v1.8 wires more skills, the hardcoded Set must track them all.
- **Wired-skill read-path coupling** — current instructions say "read `.agents/learnings/<skill>.md` directly." v1.8 S3 (`cm-learnings-researcher`) will replace direct reads with frontmatter-first filtering. Today's prose should be read-path-agnostic.
